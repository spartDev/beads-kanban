# Le SQL que la base porte (vue, colonne générée, redirection d'un nom de table) est vérifié avant chaque lecture, dans le même processus

Le garde de lecture seule (`src/server/dolt/read-only.ts`, bdesk-38k.56 et 38k.63) juge le texte de la requête, jamais ce que la base contient. Or Dolt exécute du SQL qui est dans la base, ou lit une autre table que celle que la requête nomme : une **vue** (`select … from issues` lit la vue `issues` si la base en a une, avec n'importe quelle définition, `load_file('<fichier>')` ou `dolt_query_diff('select … into outfile …', …)` compris), une **colonne générée** (`title varchar(500) generated always as (load_file(…)) virtual`, évaluée à chaque lecture, de la table comme de son historique) et une **ligne de `dolt_nonlocal_tables`**, la table système qui fait résoudre un nom de table vers une autre table, portant elle-même une colonne générée (bdesk-38k.74, relecture finale). Le contenu d'une base beads vient d'un remote partagé : un collaborateur peut commiter l'un ou l'autre, et la lecture ordinaire de l'app rend alors le contenu d'un fichier de la machine, ou crée un fichier (relevé par la relecture finale de bdesk-38k.63, N1, antérieur à .63). La portée dépend de la façon dont Dolt est lu (bdesk-38k.74). **Sans serveur** (un Projet embedded), `dolt sql` lit les fichiers de la base lui-même et pose `secure_file_priv` sur le dossier de la base : `load_file` et `into outfile` n'en sortent pas. **Derrière un `dolt sql-server`, rien ne la borne** : `secure_file_priv` y est vide (le serveur s'en alarme lui-même au démarrage : « secure_file_priv is set to "", which is insecure »), et la vue lit ou crée n'importe quel fichier que l'utilisateur peut lire ou écrire. C'est le cas de tout Projet en mode **server** (bd lance `dolt sql-server --config .beads/dolt-server-config.yaml` depuis `.beads/dolt` ; le fichier qu'il écrit règle le journal, l'hôte, le port, `cfg_dir` et le ramasse-miettes, et ne pose pas `secure_file_priv`) et de tout Projet embedded dont quelqu'un a lancé un serveur (le CLI s'y connecte de lui-même : bdesk-38k.44). Avant bdesk-38k.69, un Projet en mode server pouvait donc faire lire à l'app tout fichier lisible par l'utilisateur, et créer un fichier partout où il peut écrire. La vérification ci-dessous est du SQL que le CLI envoie à Dolt, avec chaque lecture : elle s'exécute de même sans serveur et derrière un serveur (des tests avec un vrai Dolt la passent dans les deux modes, voir plus bas), et derrière un serveur elle est la seule défense. Mesuré sur dolt 2.5.0 :

- `secure_file_priv` vaut le dossier de la base sans serveur, et la chaîne vide derrière un serveur lancé comme bd le fait. Un fichier hors du dossier de la base est alors lu par `load_file` et un autre créé par `into outfile` (et par la vue sur `dolt_query_diff('select … into outfile …', …)`, lue comme l'app la lit : `start transaction read only; select …`) ; sans serveur, `load_file` rend `NULL` et `into outfile` est refusé (« The MySQL server is running with the --secure-file-priv option so it cannot execute this statement »).
- **`information_schema.views` n'est pas la liste des vues du working set** (bdesk-38k.74, relecture) : Dolt n'y met que celles qu'il sait analyser contre le working set. Une vue dont le corps nomme une table que HEAD a et que le working set n'a plus (un working set modifié sans commit : on pointe la vue `labels` sur `lr`, puis on retire `lr`) en est absente, alors que `information_schema.tables` la liste (`VIEW`), comme `show full tables`. Or `… as of 'HEAD'`, la forme de toutes les lectures de l'app et celle de la seconde assertion, résout la vue du working set, l'analyse contre HEAD, où la table existe, et l'exécute : fichier lu, fichier créé (hors de la base derrière un serveur), contenu d'un fichier cité par l'erreur de Dolt, que l'app reprenait comme raison du Projet illisible. Une vue ainsi cachée et nommée `dolt_schemas` fait exécuter la vérification elle-même, qui lit cette table ;
- c'est la vue du **working set** que Dolt exécute, même pour `… as of 'HEAD'` (une vue qui n'est que dans le commit n'est pas résolue) ; une vue peut porter le nom d'une table système (`dolt_log`, `dolt_status`, `dolt_schemas` : `create view` l'admet, et la vue masque la table), y compris celle que la vérification elle-même lit ;
- **`dolt_nonlocal_tables`** : les colonnes `(table_name, target_ref, ref_table, options)`. Une ligne fait résoudre `table_name` (un motif : `*`, `?` et `%` y sont des jokers, comparés au nom en minuscules) vers la table `ref_table` de la référence `target_ref` (le working set d'une branche, ou un commit, un tag), avant toute autre résolution : avant les tables système (`dolt_log`, `dolt_history_*`, `dolt_status`, `dolt_schemas`) comme avant les tables ordinaires ; `options` doit valoir `immediate`. Une colonne générée de la table cible est évaluée à la lecture. Un collaborateur qui commite une ligne qui mène `dolt_history_issues` (que `history.ts` lit sans `as of`) ou `issues` (lue `as of 'HEAD'`) vers une table ordinaire dont une colonne est `generated always as (load_file(…)) virtual` fait lire à l'app un fichier (hors de la base derrière un serveur) : les deux assertions sur les noms lus passent, car `information_schema` ne parle que des tables physiques (il ne liste ni la redirection ni, sous le nom lu, la colonne générée, qui est sur une autre table), le working set est propre (tout est commité : l'attaque voyage par le remote) et aucune vue n'est en cause ;
- **la table se cache d'elle-même** : `select count(*) from dolt_nonlocal_tables` passe, comme tout nom, par la résolution, et une ligne qui mène `dolt_nonlocal_tables` vers une table vide (ou un motif qui la couvre) la fait lire vide : elle dit 0 ligne alors qu'elle en a, et `drop table dolt_nonlocal_tables` supprime alors la table vide. Aucune lecture de la table par son nom ne dit la vérité ;
- **les fonctions de table ne passent pas par cette résolution** : `dolt_log`, `dolt_schema_diff`, `dolt_diff_summary` et `dolt_diff_stat` comparent des racines ou des commits sans résoudre de nom de table (un motif `%` qui mène tous les noms vers une table sleep n'en change aucun résultat). Mais `dolt_diff_summary` ne montre pas une table **ajoutée ou supprimée** que `dolt_ignore` couvre (un motif `%` suffit : mesuré), alors que `dolt_schema_diff` et `dolt_diff_stat` la montrent ; et `dolt_diff_stat` d'une table qui n'existe pas échoue, ce que Dolt voit à l'analyse, avant d'exécuter quoi que ce soit : aucun test d'existence ne peut le précéder dans la même instruction ;
- **bd 1.x remplit puis vide `dolt_nonlocal_tables`** (bdesk-38k.74, relecture finale). Sa migration 0040 y insère quatre lignes, une par commit (`wisps`, `wisp_*`, `repo_mtimes`, `local_metadata`, vers `main`, `immediate` : « create nonlocal table wisps » et les trois suivants, puis « schema: apply migration 0040… »), et la première instruction de la 0041 (`split_dependencies_target`) les retire toutes (`delete from dolt_nonlocal_tables`, commit « disable nonlocal tables for fk migrations ») avant de modifier `dependencies` ; le binaire de bd 1.3.1 porte aussi les réparations d'une migration interrompue entre les deux. Les deux migrations sont dans bd 1.0.5 ; les sources de bd 0.47.1 et 0.49.4 (722 et 904 fichiers Go) ne citent jamais la table. **Une base migrée la porte donc, vide.** Mesuré sur les copies de cinq Projets réels (109 à 677 commits) : absente du premier commit, présente à partir du commit n° 42, 42, 82, 115 ou 293 (cinq commits où elle porte des lignes, puis le `delete`), même empreinte (`dolt_hashof_table` : `ohoebkb57f9584e290onpdtlt2jp4bc3`), 0 ligne dans HEAD et dans le working set ; de même dans la base neuve d'un `bd init` (bd 1.3.1, jetable, avec trois tickets et deux dépendances). Refuser la table qui existe refuserait tous les Projets ; la refuser quand elle porte des lignes ne refuse que la base que bd est en train de migrer (du premier commit de la 0040 au `delete` de la 0041) ou dont la migration s'est arrêtée là, jusqu'à la prochaine commande bd, qui l'achève ;
- ni un déclencheur (il ne part que d'une écriture), ni un événement (le planificateur n'a relancé un événement toutes les secondes ni pendant un processus `dolt sql` de plusieurs secondes ni pendant que le serveur tournait huit secondes), ni une procédure (elle ne part que d'un `call`, que le garde refuse) ne s'exécute à la lecture ;
- bd crée lui-même deux vues, `ready_issues` et `blocked_issues`, dans toutes ses bases (relevé sur cinq copies de bases réelles) : « aucune vue » refuserait tous les Projets.
- **Un index fonctionnel est une colonne générée *cachée*** (bdesk-38k.74, round 3, B-FI de la relecture finale, MySQL 8/Dolt 2.5.0 : `create index fi on t ((expr))`). Dolt la range comme une colonne générée virtuelle sans nom visible, et **évalue son expression à chaque lecture de la table** (`select … as of 'HEAD'`, `dolt_history_*` compris : mesuré, un index `((sleep(3)))` sur `issues` fait durer 3,3 s une lecture qui en durait 0,4, et `dolt_history_labels` 6,6 s pour deux lignes), mais **ni `information_schema.columns` ni `show full columns` ne la listent** : les deux assertions existantes, bâties sur ces deux lectures, passaient. Elle est visible par `information_schema.statistics.expression` (colonne non vide pour la ligne de cet index, sans l'évaluer : mesuré, aucun délai même non commitée) et par le texte de `show create table …` ou de `dolt_schema_diff(…).to_create_statement`, qui la montre comme n'importe quelle clé (`KEY \`fi\` ((expr))`), sans l'évaluer non plus. `from_base64(concat(repeat('A', conv(hex(substr(load_file(f),1,3)),16,10)), '!')))` en fait un oracle d'un octet par lecture (voir plus haut, « le texte d'une erreur de Dolt ») ; `((sleep(n)))` un déni de service. Elle échappe aux mêmes refuges qu'une colonne générée ordinaire (le working set comme HEAD, une ancre d'époque) et à un de plus : `show full columns from <table> as of 'HEAD'`, que le diagnostic lit pour HEAD (« HEAD et le working set », plus bas), ne la voit pas davantage. Ce cas-là, un index que HEAD porte encore et que le working set modifié a retiré, est fermé par le `CREATE TABLE` de HEAD confronté à la grammaire fermée (plus bas), que le diagnostic lit dans le même groupe que ces colonnes.

## Considered Options

- **Refuser toute base qui a une vue** — rejeté : fausse alerte sur toutes les bases beads.
- **Une vérification dans un processus à part, mémorisée par HEAD** (la piste du ticket) — rejetée : un commit, ou une vue du working set, qui arrive entre la vérification et la lecture est exécuté ; et le HEAD seul ne dit rien du working set, que Dolt exécute.
- **Restreindre `secure_file_priv` pour les processus que l'app lance** — impossible : la variable est en lecture seule (`set` la refuse, `set persist` aussi), la configuration persistée (`sqlserver.global.secure_file_priv`, globale ou de la base) et l'environnement n'y font rien, et `dolt sql` la pose sur son dossier de données, que l'app ne peut pas rendre plus étroit que celui de la base (`--data-dir` ou `-C` l'élargissent au dossier parent ; un lien symbolique vers la base n'est pas suivi). Un bac à sable du système ne se porte pas d'un poste à l'autre. Et la question ne se pose même pas pour un serveur que l'app ne lance pas (celui de bd, ou celui qu'un utilisateur a lancé) : `secure_file_priv` y est vide, et la configuration du serveur n'est pas à l'app. Sans serveur, le dossier de la base borne déjà la portée sans qu'on puisse la resserrer ; derrière un serveur, rien ne la borne. **Aucune défense en profondeur de ce côté : la vérification avant chaque lecture est la défense, et la seule en mode server.**
- **Deux instructions qui précèdent chaque lecture, dans le même processus** — retenu. Dolt s'arrête à la première erreur d'un groupe : une sous-requête scalaire qui rend plusieurs lignes (« the subquery returned more than 1 row ») dès qu'il y a du SQL stocké empêche la lecture de partir. Aucun délai ne sépare la vérification de la lecture : la base est vérifiée dans l'état exact où elle est lue.
- Pour `dolt_nonlocal_tables`, **lire la table par son nom et refuser s'il y a des lignes** — rejeté : elle se cache d'elle-même. **La refuser dès qu'elle existe** — rejeté : bd la crée, vide. **La lire par `dolt_diff_summary` seul** — rejeté : `dolt_ignore`, que bd emploie, cache la table ajoutée. **La lister par `information_schema.tables`** — rejeté : il ne liste pas les tables système, et avec `dolt_show_system_tables` il échoue dès que la table existe (« expected Alterable or WritableDoltTable »). **`dolt_hashof_table('dolt_nonlocal_tables')`** — rejeté : il échoue si la table n'existe pas, donc ne peut pas servir d'assertion. **Lire le schéma résolu de chaque nom lu (`show full columns`)** — rejeté pour la lecture ordinaire : un `show` ne se met pas sous une assertion, la lecture partirait avant qu'on en sache le résultat, et le diagnostic s'en sert pour HEAD. **Admettre les quatre lignes de bd** (`wisps`, `wisp_*`, `repo_mtimes`, `local_metadata`) — non retenu : elles ne mènent aucun nom que l'app lit, mais les distinguer d'autres lignes demande de lire le contenu de la table sans la nommer (une fonction de table de plus, `dolt_diff` sur une table système, non mesurée), pour ne servir que les quelques secondes d'une migration ; refuser toute ligne est plus simple et ne se trompe pas dans le sens dangereux. À reprendre si un bd futur laissait des lignes au repos : toutes ses bases seraient alors refusées, bruyamment, avec cette raison. **Compter ce que la table porte par `dolt_schema_diff` et `dolt_diff_summary` contre un commit où elle manque** — retenu (« `dolt_nonlocal_tables` », plus bas).
- Pour fermer B-FI et tout mécanisme du même genre, **une liste noire d'expressions interdites dans un index, un défaut ou un `check`** (`sleep`, `load_file`, `from_base64`…) — rejetée : c'est la forme même qui a fait tomber les deux assertions précédentes (vues, colonnes générées) à chaque round, une liste noire ne protège que contre ce qu'on a déjà vu. **Une liste blanche d'expressions admises à la même place** — rejetée pour la même raison dans l'autre sens : il faudrait relister chaque fonction inoffensive, et une liste de fonctions ne dit rien des combinaisons. **Retenu : une liste blanche de la grammaire du `CREATE TABLE` lui-même** (`create-table.ts`) — pour chaque table lue, dans chaque état lu (working set, HEAD, l'ancre d'une époque), le texte complet du `CREATE TABLE` (lu par une fonction de table qui ne résout aucun nom, jamais par `show create table`, voir plus bas) doit être entièrement composé de colonnes à type littéral, de clés et de clés étrangères dont les parties sont des noms de colonnes (une longueur de préfixe admise), d'options de table, et d'un petit nombre de formes de défaut et de `check` mesurées sur des bases bd réelles (plus bas) : tout le reste — `GENERATED`, un index fonctionnel, un `check` qui appelle une fonction, un défaut entre parenthèses qui n'est pas l'une des formes admises, et toute construction non prévue par cette grammaire — est refusé. Écrite comme un petit analyseur descendant sur les jetons du texte (`tokenize`/`Cursor`), pas comme des expressions régulières qui chercheraient ce qui est dangereux.

## Consequences

- **Quoi** (`src/server/dolt/stored-sql.ts`). Les noms que l'app lit (`reader.ts`, `history.ts`) : `issues`, `dependencies`, `labels`, `comments`, `config` et les tables système `dolt_history_issues`, `dolt_history_dependencies`, `dolt_log`, `dolt_commit_ancestors`. Une vue qui porte l'un de ces noms, ou celui d'une table que la vérification lit (`dolt_schemas`, `dolt_status`), est refusée ; une colonne générée d'une de ces tables aussi ; une table `dolt_nonlocal_tables` qui porte des lignes aussi, quel que soit le nom qu'elle mène ailleurs. `ready_issues` et `blocked_issues` ne sont jamais lues : elles sont admises. **Une lecture de plus d'une table, ou d'une autre, se déclare dans cette liste** : `stored-sql.test.ts` refait chaque lecture de l'app et échoue si elle nomme une table que la liste ne surveille pas.
- **Les noms ne se comparent que dans Dolt, jamais en JavaScript.** Dolt lit un nom à sa façon : `Issues` est `issues` ; une vue `issueſ` (U+017F, le « s long ») est lue comme `issues` (il replie la casse à l'unicode), alors que `'ſ'.toLowerCase()` reste `ſ` ; `İ` (U+0130) est ramené à `i` quand Dolt crée la vue. Une comparaison en JavaScript manque ce que Dolt réunit, et c'est un trou : la relecture de bdesk-38k.69 en a trouvé deux (une table `Issues` que `dolt_status` écrit autrement, une vue `dolt_history_dependencieſ`). Toute comparaison de nom se fait donc **dans Dolt** : par sa collation (`information_schema.tables` et `.columns`, `dolt_schemas.name`, qui ignorent la casse et plus : un balayage de 1 124 caractères que la casse, la compatibilité ou les accents rapprochent d'une lettre des noms lus n'a trouvé, pour les vues, que `ſ` et `İ` que Dolt lise comme un nom lu, et aucun que ces comparaisons laissent passer ; pour les tables, que `İ`, de même), ou par sa résolution même (`show full columns from <nom lu> as of 'HEAD'`). **`to_table_name` de `dolt_schema_diff` et `dolt_diff_summary` est, lui, en collation binaire** (`utf8mb4_0900_bin`, mesurée) : contrairement à une version antérieure de cette ADR, ces deux fonctions de table **ne replient pas la casse** d'elles-mêmes, et Dolt résout pourtant une table sans en tenir compte. `nonlocalCount` et `nonlocalAt` (bdesk-38k.74, round 3, R1 de la relecture finale) comparent donc `lower(to_table_name) = 'dolt_nonlocal_tables'`, pas `to_table_name = …` ; `lower` est sur la liste blanche du garde de lecture seule pour cette seule raison. **Round 4 : `schemaCreateSql` (le `CREATE TABLE` de chaque table lue, plus bas) avait la même faute** : il filtrait `to_table_name in ('issues', …)`, et manquait donc une table que HEAD nomme `Issues`, `ISSUES` ou `İssues` (mesuré, une base sans `issues` portant l'une d'elles : `select … from issues` la lit, `information_schema.statistics` la rend sous `table_name in ('issues')`, `show full columns from issues as of 'HEAD'` la lit, et `dolt_schema_diff` la nomme telle quelle, que la comparaison exacte manque et que `lower(to_table_name) in (…)` retrouve). Il compare maintenant `lower(to_table_name)`. `issueſ` (U+017F) n'est pas lue comme `issues` (mesuré : « table not found »), et `lower('issueſ')` reste `issueſ` : les deux sont d'accord. Les noms de table physiques que Dolt lit comme l'un des cinq noms de l'app, d'après le balayage ci-dessus et les minuscules simples d'Unicode que Go applique, sont donc ces noms écrits avec des majuscules ASCII, et `İ` (U+0130) pour un `i` (le signe Kelvin, U+212A, se ramène à `k`, qu'aucun des cinq noms n'a) : `lower(…)` les ramène tous à la forme de la liste. Le seul nom comparé en JavaScript l'est à une liste fermée, par égalité exacte, avec le refus pour cas par défaut (les deux vues de bd). `stored-sql.test.ts` le pin : aucun `toLowerCase`, `toUpperCase` ni comparaison locale dans `stored-sql.ts`.
- **Dans quel ordre, et ce que la première lit.** La première instruction ne lit que `information_schema.tables`, hors des tables de base (`table_type <> 'BASE TABLE'`), et non `information_schema.views` : `.tables` liste toute vue, y compris celle que Dolt ne sait pas analyser dans le working set, sans l'analyser ni l'exécuter (mesuré sur 24 formes de vues, cachées ou non, noms repliés compris, avec une charge qui écrit un fichier ou qui dort deux secondes, embedded et derrière un serveur : aucun fichier créé, aucun délai). Elle compte aussi ce que `dolt_nonlocal_tables` porte, par des fonctions de table (voir plus bas). Une vue ou une table de la base qui porte le nom d'un objet d'`information_schema` (`tables`, `columns`, `views`, `schemata`, `information_schema`, en majuscules aussi) ne change ni ce que la première lit ni ce qu'elle exécute (mesuré). Elle passe en premier : une vue nommée `dolt_status` ou `dolt_schemas`, cachée ou non, ou une ligne de `dolt_nonlocal_tables` qui les mène ailleurs, ferait exécuter la seconde, qui lit ces tables (`dolt_schemas as of 'HEAD'` exécute la vue du working set), avant qu'elle ait rien dit. La seconde lit les vues de HEAD, les colonnes générées du working set (`information_schema` ne se lit pas `as of`) et `dolt_status`. **Toute instruction de la vérification qui lit un nom qu'une vue ou une redirection peut mener ailleurs vient après la première assertion** : la seconde, les trois temps du diagnostic (`show full columns … as of 'HEAD'` compris) et le dernier essai ; les seules qui la précèdent ne lisent qu'`information_schema` et des fonctions de table qui comparent des racines. Un audit lance chacun de ces groupes, tel que le code l'envoie, contre 60 bases hostiles : 52 de vues (cachées ou non, noms repliés compris, charge qui écrit un fichier ou qui dort deux secondes) et 8 de `dolt_nonlocal_tables` (un motif qui mène tous les noms vers une table qui dort, chaque nom un à un, commités ou non, avec `dolt_ignore` qui couvre tout, la table qui se cache d'elle-même) ; 11 groupes chacune (l'assertion des vues, les deux assertions, le groupe du dernier essai, les trois temps du diagnostic, chaque relevé seul, la recherche du commit de base et sa sonde), soit 660 groupes embedded puis 660 derrière un `dolt sql-server` qui n'a pas de `secure_file_priv`. Aucun n'a créé de fichier, aucun n'a duré deux secondes (le pire : 389 ms embedded, 405 ms derrière le serveur), aucun n'a échoué autrement que par son assertion ou par le message fixe de la vérification, et aucune assertion n'a passé sur une base de `dolt_nonlocal_tables`. Le témoin, la lecture de `dolt_schemas as of 'HEAD'` sans l'assertion devant elle, exécute bien la vue (12 bases de vues sur 52 : celles dont la vue porte un nom de `dolt_schemas`, cachée ou non, charge fichier ou `sleep`) et suit la redirection (5 des 8 bases de `dolt_nonlocal_tables`, celles dont une ligne mène un nom que la vérification lit : il échoue ; les 3 autres ne mènent que des noms de l'app, et l'assertion les nomme).
- **`dolt_nonlocal_tables`** (bdesk-38k.74, relecture finale). Elle est refusée si elle porte des lignes, dans le working set ou dans HEAD, et se lit sans la nommer. La première assertion compte, pour chacune des deux racines (`'WORKING'`, `'HEAD'`), les tables `dolt_nonlocal_tables` non vides par `dolt_schema_diff` et `dolt_diff_summary` contre un **commit de base** où elle n'existe pas : par rapport à lui, la table est « ajoutée » (`from_table_name` vide) et `data_change` dit si elle a des lignes. Une table que `dolt_schema_diff` montre et que `dolt_diff_summary` ne montre pas (`dolt_ignore` la cache) compte comme non vide, et une table qui n'est pas ajoutée par rapport au commit de base aussi. Aucun nom de table n'est résolu : une ligne de la table ne peut ni la cacher ni mener la comparaison ailleurs. Le commit de base est le premier commit de la lignée de HEAD (`dolt_log('HEAD') order by commit_order asc limit 1`), cherché **une fois par base, avant sa première lecture**, et vérifié : `dolt_diff_stat` de ce commit contre lui-même échoue « table not found » s'il n'a pas la table. S'il l'a déjà (une histoire fabriquée), la base est refusée : sans commit où la table manque, on ne peut pas dire qu'elle est vide. Le commit de base disparaît si l'histoire est réécrite : la première instruction de la lecture échoue alors, avant tout le reste, et il est cherché de nouveau. Sans lui, la première assertion échoue toujours. Le diagnostic relève les comptes (`working`, `head`) pour nommer la table ; ses deux derniers temps portent le commit de base dans leur assertion des vues. Une époque du schéma des dépendances (`<base>/<commit>`, où Dolt résout les noms avec la table de ce commit-là, `dolt_history_dependencies` compris) est comptée de même contre le même commit de base, **avant que son nom soit lu** (`DoltDatabase.storedSqlAt`, que `withOptions` conserve). Une ligne qui mène un nom que la vérification lit elle-même (`dolt_schemas` surtout : Dolt ne sait plus résoudre une vue, « expected a SchemaTable ») fait échouer toute instruction qui nomme une table : la base est refusée, par le message fixe de la vérification, sans que le texte de Dolt soit repris ; les fonctions de table, elles, ne sont pas redirigées (mesuré : un motif `%` vers une table qui dort deux secondes ne change ni ne ralentit aucune de leurs instructions). Derrière un serveur qui sert plusieurs bases, `information_schema.tables` parcourt toutes celles qu'il sert : une base de ce genre fait refuser de même les bases saines qui partagent son serveur (mesuré : refusées, jamais lues de travers) ; le serveur d'un Projet en mode server ne sert que les bases du dossier `.beads/dolt` de ce Projet. **R5 du round 3 (nommer la base voisine responsable) est RETIRÉE au round 4.** `information_schema.tables` est cassée server-wide par la redirection d'une voisine, la base saine est refusée par le message fixe de la vérification, et ce message ne nomme personne : la recherche de la voisine (`culpritDatabase`, round 3) lançait `` select count(*) from `<base>`.dolt_nonlocal_tables `` contre chaque base du même serveur (vingt au plus) par le client brut, **sans la vérification**. Une base voisine peut définir une **vue** qui porte ce nom (Dolt l'accepte : elle masque la table système, mesuré), et lire une vue en exécute le corps : `dolt_query_diff('select … into outfile …')` écrit un fichier hors de toute base, derrière un serveur sans `secure_file_priv`. Le relecteur l'a fait (trois bases sur un serveur : `tdb` saine, `evil` dont la table de redirection casse `dolt_schemas`, `aaa` dont la vue écrit `PWNED-BY-STORED-SQL` hors de toute base : le fichier existait après la lecture de `tdb`). La recherche est supprimée, non réparée : elle n'améliorait qu'un message. Un test d'intégration (`stored-sql.neighbour.integration.test.ts`, trois bases sur un serveur, rouge avant et vert après) le garde. **La raison de `dolt_nonlocal_tables` non vide tient maintenant en une seule phrase** (round 3, R3 de la relecture finale) : avant, le working set et HEAD non vides faisaient chacun leur propre phrase technique (« Dolt y lit des noms de tables menés vers d'autres tables… ») ; comme la cause la plus probable est une migration de bd en cours (plus haut), la raison dit maintenant platement cela, une fois, avec quoi faire — réessayer, ou laisser n'importe quelle commande bd l'achever — plutôt que d'expliquer le mécanisme. **Limite** : un commit de base où `dolt_nonlocal_tables` manque suppose que le premier commit d'une base de bd est celui de `dolt init`, sans table (relevé sur les cinq copies : bd la crée à sa migration 0040, du 42ᵉ au 293ᵉ commit). **Round 4 : cette hypothèse est maintenant vérifiée, et plus seulement supposée.** `dolt_schema_diff` et `dolt_diff_summary` ne rendent que ce qui diffère entre leurs deux racines : une table que le commit de base porte déjà et que HEAD n'a pas changée n'y figure pas, et son `CREATE TABLE` (un index fonctionnel, voir plus bas) ne serait jamais jugé. Mesuré : `dolt commit --amend` sur le commit d'`init` y met les tables, et `dolt_schema_diff(<ce commit>, 'HEAD')` ne rend alors aucune ligne, alors qu'une lecture de HEAD évalue l'index. Un collaborateur qui tient le remote fabrique cette base ; la vérification la refuse donc : après la sonde de `dolt_nonlocal_tables`, `learnBase` lit la liste de la révision du commit de base (`show full tables from \`<base>/<commit>\``, `revisionTablesSql`) et **refuse la base si elle n'est pas vide**, tables et vues comprises (« existe déjà dans le premier commit : sans commit où elle manque, on ne peut pas juger son CREATE TABLE »). Mesuré sur les cinq copies de Projets réels et sur une base neuve de bd 1.3.1 : le commit « Initialize data repository » a une liste vide, et aucune des six n'est refusée. `show full tables as of '<commit>'`, plus simple, ne convient pas : il liste les vues du working set (`ready_issues`, `blocked_issues`) même pour un commit qui n'en a pas. **Limite de cette vérification** : un clone superficiel (`dolt clone --depth N`) a pour premier commit visible celui où il a été coupé, qui porte déjà les tables (mesuré) : il est refusé de même, bruyamment, jamais lu sans vérification. Les deux opérations de bd qui réécrivent l'histoire gardent ce premier commit (mesuré sur une base jetable de bd 1.3.1, 85 commits : `bd flatten --force` puis, sur une copie, `bd compact --days 0 --force` rendent chacun deux commits, le `dolt init` sans la table puis le cliché, et l'app lit les deux bases comme avant). Une version de Dolt qui mettrait la table vide dans le premier commit, ou un autre outil qui ferait une histoire sans commit d'avant la table, ferait refuser la base, bruyamment, avec cette raison.
- **Index fonctionnel et grammaire fermée du `CREATE TABLE`** (bdesk-38k.74, round 3, B-FI de la relecture finale). Deux niveaux, l'un devant l'autre :
  1. **Tier 1, dans la première assertion** : `information_schema.statistics` du working set, filtrée sur les tables lues et `expression <> ''`, compte les index fonctionnels comme `.tables` compte les vues (même emplacement, même garantie d'abandon par Dolt avant que la lecture ne parte : mesuré, aucun délai même sur un index non commité, par les « faits » de `stored-sql.functional-index.integration.test.ts`). Elle ne dit rien de HEAD : `information_schema` ne se lit pas `as of`.
  2. **Tier 2, deux instructions de plus à chaque groupe de lecture, au dernier essai comme aux autres** (`schemaProbe`) : le `CREATE TABLE` de chacune des cinq tables lues, dans le working set puis dans HEAD, lu par `dolt_schema_diff(<commit de base>, 'WORKING'|'HEAD')` comme `nonlocalCount` lit `dolt_nonlocal_tables` — sans résoudre aucun nom de table, donc sans suivre ni être trompé par une redirection (déjà refusée avant que ceci ne soit lu) — jamais par `` show create table `<base>/<commit>`.dependencies `` : **ce texte contient les mots nus `create` et `table`, que le garde de lecture seule refuse où qu'ils s'écrivent** (`FORBIDDEN_WORDS`), sans égard pour le `show` qui les précède ; mesuré en voulant l'employer pour l'ancre d'une époque (round 3), il est refusé par le garde avant même d'atteindre Dolt. Les noms se comparent en `lower(d.to_table_name)` (round 4, plus haut) **depuis les cinq noms que la requête écrit elle-même** (m2, round 4 : une jointure à gauche, `expected` / `tbl` / `stmt`, une ligne par table attendue, `tbl` et `stmt` absents quand la comparaison n'a rien pour elle) : une table lue dont la comparaison ne rend aucune ligne, ou dont la ligne n'a pas de texte, est **refusée** (« aucune définition de table lue par la comparaison : la table manque, ou la comparaison est incomplète »), au lieu d'être acceptée faute de ligne comme avant. Le commit de base vide n'est plus la seule chose qui rende la comparaison complète. À l'ancre d'une époque, l'app ne lit que l'historique des dépendances : seule `dependencies` est exigée, les autres sont jugées si la comparaison les rend (une histoire ancienne peut ne pas les avoir). Le commit de base est sans aucune table (round 4, voir la limite de la section sur `dolt_nonlocal_tables`) : sans cela, une table que ce commit porte déjà et que HEAD n'a pas changée n'apparaîtrait pas dans la comparaison. Chaque texte est confronté à la grammaire fermée de `create-table.ts` (l'option retenue, plus haut). **Ce verdict arrive après la lecture** : ce n'est pas une assertion qui abandonne le groupe, Dolt a déjà pu exécuter la lecture. Ses lignes ne sont donc rendues à l'appelant qu'une fois le verdict propre, sinon elles sont jetées, et le texte de l'erreur de Dolt n'est jamais repris (« Le texte d'une erreur de Dolt n'est jamais rendu », plus bas). **Ce qui n'attend pas ce verdict : la première lecture d'un HEAD.** Un index que HEAD porte et que le working set modifié a retiré échappe à Tier 1 (qui ne lit que le working set) : sans autre garde, la première lecture, `as of 'HEAD'`, l'évaluerait, et le verdict ne viendrait qu'après. Le diagnostic lit donc le `CREATE TABLE` de HEAD (`headColumns`) dans le même groupe que `hashof('HEAD')` et les colonnes de HEAD, et le juge **avant de retenir ce HEAD** : tant que HEAD n'est pas retenu, l'assertion arrête la lecture, le diagnostic la refuse, aucune lecture ne part (mesuré : refusée en moins de six secondes, alors que lire l'index en prend huit de plus, une base de HEAD à `issues` et une à `Labels`, embedded et derrière un serveur). L'ancre d'une époque du schéma des dépendances est fermée de même, dans `storedSqlAt` (donc avant que son nom ne soit lu, comme pour `dolt_nonlocal_tables`), par `dolt_schema_diff` contre ce commit-là plutôt que `'WORKING'`/`'HEAD'` : mesuré sur un index fonctionnel qui n'existe que dans l'ancien schéma, avant une migration qui l'aurait sinon emporté hors de portée de Tier 1 et Tier 2 courants.
  3. **Ce que bd pose dans ses `CREATE TABLE`, mesuré** (cinq copies de Projets réels, identiques entre elles : une seule empreinte de `CREATE TABLE` par table, dans le working set comme dans HEAD) : aucune colonne générée, aucun index fonctionnel ; quatre clés étrangères, toutes `REFERENCES `issues` (`id`) ON DELETE CASCADE ON UPDATE CASCADE` (`fk_dep_issue` et `fk_dep_issue_target` sur `dependencies`, `fk_labels_issue` sur `labels`, `fk_comments_issue` sur `comments`) ; une seule contrainte `check`, `ck_dep_one_target` sur `dependencies` (une somme de trois `not(… is null)` égale à 1) ; un défaut entre parenthèses, `` `metadata` json DEFAULT (json_object()) ``, dans `issues` et dans `dependencies`. **À l'ancre d'une époque** (le dernier commit d'avant la migration 0041, que l'historique relit : `storedSqlAt` lit alors le `CREATE TABLE` de ce commit-là, des cinq tables) **le schéma d'avant, relevé sur trois des cinq copies** : `` `comments`.`id` char(36) DEFAULT (uuid()) ``, des dates `DEFAULT 'CURRENT_TIMESTAMP'` (une chaîne, que Dolt écrivait ainsi), des clés étrangères sans `ON UPDATE`. Cette forme a d'abord été refusée (`(uuid())` n'était pas sur la liste) : l'historique de ces trois Projets était illisible, une fausse alerte que la mesure sur les copies, ancres comprises, a trouvée ; `(uuid())` est donc admis, comme `(json_object())`. Refuser clés étrangères, `check` ou défauts entre parenthèses en bloc refuserait tous les Projets de bd à jour : la grammaire fermée les admet par leur forme, pas davantage. Une clé étrangère : `constraint` nom `foreign key` (noms de colonnes) `references` table (noms de colonnes), et des `on delete`/`on update` dont l'action est l'un des cinq mots de MySQL. Un `check` : comparaisons, `is [not] null`, `not`, `and`/`or`, `+`/`-`, parenthèses, noms de colonnes et nombres, **jamais un appel de fonction, une chaîne, un nom qualifié ou une sous-requête**. Un défaut entre parenthèses : `(json_object())` ou `(uuid())` exactement (`ZERO_ARGUMENT_DEFAULTS` : aucun argument, rien d'attaquant-contrôlé), ou — mesuré pendant ce round sur une base d'essai, après un `alter table` qui ajoute puis retire un index fonctionnel — **une chaîne ou un nombre littéral entre parenthèses, `` `type` varchar(32) DEFAULT ('blocks') `` : Dolt range ainsi un défaut ordinaire après certains `alter table`, sans qu'aucun appel n'y entre**. Toute autre forme — un `check` qui appelle une fonction, un défaut `(sleep(1))` ou `(1+1)`, une clé étrangère dont l'action n'est pas l'un des cinq mots, une clé ou un défaut avec une autre expression — est refusée, y compris une qu'on n'aurait pas imaginée : la grammaire est fermée, pas une liste de motifs à éviter. **L'imbrication d'un `check` est bornée** (m1, round 4) : l'analyseur descend par récursion, et Dolt accepte un `check` de vingt mille `not` à la suite (il l'écrit en quelque quarante mille parenthèses imbriquées) : la pile débordait (« Maximum call stack size exceeded » : le Projet était refusé, mais par une exception de JavaScript). `MAX_CHECK_DEPTH` (soixante-quatre niveaux, parenthèses et `not` confondus ; bd en pose six) donne le refus générique de la grammaire au-delà.
  4. **Ce qui reste de Tier 1 (vues, colonnes générées, `dolt_nonlocal_tables`) n'est pas subsumé par Tier 2** et les deux sont gardés : Tier 1 abandonne le groupe *avant* que la lecture ne parte (une garantie que Dolt donne, pas la vérification) ; Tier 2 ne le peut pas pour un `check` ou un défaut (qui n'exécutent jamais rien à la lecture, donc rien n'abandonne le groupe pour leur cause), mais referme ce que Tier 1, bâti sur `information_schema`, ne peut pas voir pour HEAD. Les tables système que la vérification lit elle-même (`dolt_schemas`, `dolt_status`) ne sont pas probées par Tier 2 : une vue sur l'une d'elles est déjà refusée par Tier 1, et `dolt_nonlocal_tables` par `nonlocalCount`/`nonlocalAt` ; les ajouter à Tier 2 referait, plus cher, ce que ces deux font déjà.
  5. **Le coût** (CPU d'un processus `dolt sql`, mesuré sur les copies des cinq Projets réels et sur la base neuve de bd, avant et après ce round) : `information_schema.statistics` coûte, comme `.columns`, un balayage de plus dans la première assertion : elle reste à 6,2 à 7,4 ms (5,5 à 7,7 ms avant ce round : une différence dans le bruit de la mesure). Chacune des deux instructions de Tier 2 (un balayage de `dolt_schema_diff` filtré sur cinq noms : la forme du round 4, avant m2) coûte de 0,1 à 1,8 ms ; un processus de lecture entier coûte en moyenne 0,7 ms de plus (de −8,6 à +8,6 ms d'une base à l'autre : plus que l'effet cherché, donc du bruit), et le départ d'un processus, 86 à 96 ms, domine toujours. **La jointure à gauche de m2 (une ligne par table attendue) coûte, elle, plus que le filtre qu'elle remplace** (mesuré, mêmes copies, même méthode, 11 répétitions d'une instruction dans un processus moins une, minimum de 3) : de 0,0 à 1,0 ms par instruction avec le filtre (0,45 ms en moyenne sur le working set, 0,61 sur HEAD) à 1,2 à 2,9 ms avec la jointure (2,40 et 1,91 ms), soit environ 3 ms de plus par processus de lecture, qui en coûte 20 à 30 sur un départ de 86 à 96 ms.
  6. **Limite connue (m3, relecture finale, round 4) : le texte de `dolt_schema_diff` n'est pas une image complète du schéma.** Mesuré (Dolt 2.5.0) : `to_create_statement` **omet** un index secondaire qui porte exactement sur les colonnes de la clé primaire (`key k (id)` sur une clé primaire `id` ; `key k (id, n)` et `key k (n, id)` sur une clé primaire `(id, n)`), alors que `show create table` et `information_schema.statistics` le listent ; il **garde** un préfixe strict de la clé (`key k (id)` sur `(id, n)`) et un sur-ensemble (`key k (id, n)` sur `id`). L'omission ne cache rien d'évalué à la lecture : un index dont toutes les parties sont des colonnes simples n'a pas d'expression, et un index fonctionnel, seul ou mêlé aux colonnes de la clé (`km (id, ((lower(author))))`, `kf (((lower(label))), issue_id)`), figure toujours dans le texte (mesuré) et dans `information_schema.statistics`, que Tier 1 lit pour le working set. La grammaire juge donc un texte auquel peut manquer un index ordinaire, et rien d'autre : sans conséquence aujourd'hui, mais à savoir si une version de Dolt omettait un autre objet du texte. Un fait d'intégration le garde (`stored-sql.functional-index.integration.test.ts`, « m3 » : il échouerait si Dolt cessait de l'omettre, ou si le texte cessait de garder l'index mêlé).
- **La vérification ne lit que la base qu'elle vérifie, et le client brut n'est jamais exposé** (bdesk-38k.74, relecture finale, round 4 : inventaire de ce que le serveur envoie à Dolt, après `culpritDatabase`). Règles, gardées par `stored-sql.audit.test.ts` pour les chemins qu'aucun essai n'emprunte et par `stored-sql.neighbour.integration.test.ts` (trois bases sur un serveur) : (1) `createDoltClient` n'est créé que par `client.ts` et `stored-sql.ts`, qui l'enveloppe ; le service des Projets et la découverte reçoivent le client vérifié par défaut ; `client.ts` est le seul fichier qui lance un processus ; (2) aucune instruction ne liste les bases (`information_schema.schemata`, `show databases`) ni ne qualifie une table par une base : la seule autre racine que la vérification nomme est une **révision de la même base**, `` `<base>/<commit>` `` ; (3) les instructions que la vérification envoie elle-même par le client brut, toutes contre la base vérifiée, sont de trois sortes : des fonctions de table qui comparent deux commits par leur hash (`dolt_log`, `dolt_diff_stat`, `dolt_schema_diff`, `dolt_diff_summary`, qui ne résolvent aucun nom de table) ; des listes qui n'exécutent aucune vue (`information_schema.tables`, `.columns`, `.statistics`, et `show full tables from <base>/<commit>` : mesuré, y compris sur un premier commit qui ne porte que des vues nommées `dolt_schemas`, `dolt_nonlocal_tables`, `issues`… dont le corps écrit un fichier : aucun fichier) ; et, derrière la première assertion qui arrête le groupe avant elles, les lectures de tables système (`dolt_schemas as of 'HEAD'`, `dolt_status`, `show full columns … as of 'HEAD'`). Les lectures qui ne nomment aucune table (`select hashof('HEAD')`, `select database()`, sans `from`) ne passent pas par les assertions : elles ne peuvent lire aucune table. Une base voisine du même serveur ne résout jamais dans la session de la base vérifiée : seule une référence qualifiée y mènerait, et la vérification n'en écrit plus aucune (mesuré : un serveur sain dont une voisine porte, en vue, chacun des dix-huit noms que l'app ou la vérification résolvent, chacune écrivant son fichier : aucun fichier écrit).
- **HEAD et le working set.** Les lectures `as of 'HEAD'` utilisent le schéma de HEAD ; `information_schema` donne celui du working set. Quand le working set est propre (bd en auto-commit, le défaut), ils sont le même et rien ne se retient. Quand il a changé sans commit (`batch`, `off`), **une table quelconque** (`dolt_status` a une ligne, sans qu'on en compare le nom : il écrit `Issues` quand la table a été renommée ainsi, que `dolt_status` y compare ou non à `issues`), l'assertion échoue tant qu'elle ne porte pas le HEAD dont le schéma a été vérifié. Son deuxième temps lit, dans le même instantané que `dolt_status`, le hash de HEAD et les colonnes générées : si le working set est **propre** à ce moment, il est HEAD, cet instantané n'a ni vue, ni colonne générée, ni vue de HEAD, et ce HEAD est sain : il est retenu aussi, sans sonder ses colonnes. Les racines de bd diffèrent de HEAD même quand `dolt_status` est propre (ses tables locales, que `dolt_ignore` couvre, changent sans commit : sur les cinq copies, `dolt_hashof_db()` et `dolt_hashof_db('HEAD')` diffèrent partout, `dolt_status` est vide) : le « propre » est celui de `dolt_status`, non l'égalité des racines.
- **Une base de révision** (les époques du schéma des dépendances, `<base>/<commit>.dolt_history_dependencies`, `history.ts`) est relue par `show columns` (la colonne générée) et `show full tables from <base>/<commit>` : lire sa table `dolt_schemas` exécuterait la vue qui la masque (mesuré). Aucun collaborateur ne les pose par le remote ;
  - **fonctions définies par l'utilisateur** : n'existent pas (`create function` est une erreur de syntaxe) ; **`dolt_workspace_*`** et les autres tables générées : calculées par Dolt, sans SQL stocké.
- **Le coût** (CPU des processus `dolt sql`, mesuré sur les copies de cinq Projets réels et sur la base neuve de bd, 85 à 677 commits) : un processus à vide coûte 90 à 103 ms ; la première assertion passe de 1,4 à 2,4 ms avant bdesk-38k.74 à 5,1 à 6,6 ms (le compte de `dolt_nonlocal_tables` dans les deux racines ajoute 3,7 à 4,4 ms), la seconde reste à 9,8 à 13,1 ms : 15 à 20 ms de CPU par processus de lecture, 4 ms de plus que l'état précédent (la mesure d'un processus entier est dans le bruit d'une machine chargée : ±3 ms, d'un tirage à l'autre). Le commit de base se cherche en trois processus (une lecture de `dolt_log` et du nom de la base, 87 à 106 ms, puis la sonde, 87 à 94 ms, puis, depuis le round 4, la liste de la révision de ce commit, de l'ordre de 90 ms), une fois par base et par exécution de l'app ; une lecture qui ne nomme aucune table (`select hashof('HEAD')`, le sondage du direct, ADR 0002) n'en porte pas. Les deux instructions de `CREATE TABLE` de Tier 2 y ajoutent 0,1 à 1,8 ms chacune avec le filtre du round 4, 1,2 à 2,9 ms avec la jointure à gauche de m2 (mesuré, voir « Index fonctionnel et grammaire fermée du `CREATE TABLE` », point 5). Chaque balayage de `information_schema` est compté dans une table dérivée du `from`, ce qui coûte moitié moins que dans la sous-requête scalaire. La recherche du commit de base (trois processus) a lieu une fois par base et par exécution de l'app. Un diagnostic (deux à trois processus) n'a lieu qu'à la première lecture d'une base dont le working set est modifié sans commit, puis à chaque commit tant qu'il l'est. Le dernier essai d'une lecture, que seule une base qui change sous la vérification amène jusque-là, paie en plus un second balayage d'`information_schema` (voir « Une base qui change pendant la vérification »).
- **Où il s'installe** : `createCheckedDoltClient`, le client par défaut de `createProjectService` et de `discoverProjects`. Un client passé à la main (les essais, avec un faux `dolt`) n'a pas la vérification : seuls les essais le font.
- **Le refus** est un `StoredSqlError`, une `DoltQueryError` : un Projet illisible (503 « Projet illisible : … SQL stocké dans la base… »), dont la raison nomme l'objet (sans citer son contenu). **Elle est bornée** : une base porte autant d'objets qu'on veut (des centaines de colonnes générées, des centaines de vues dans une ancre d'époque), et la raison part telle quelle dans la réponse. Elle en nomme **cinq au plus** (`MAX_NAMED_OBJECTS`), puis dit combien d'autres (« … ; et 295 autres »), et chaque nom est coupé à **64 points de code**, jamais au milieu d'une paire de substitution, ses caractères de contrôle et ses séparateurs de ligne et de paragraphe d'Unicode (U+2028, U+2029) devenant `?` (un point de code et non un graphème : la borne ne dépend de rien, un graphème peut porter autant de marques combinantes qu'on veut, et couper l'un d'eux en deux est sans conséquence). Elle ne dépasse ainsi jamais quelques milliers de caractères.
- **Le texte d'une erreur de Dolt n'est jamais rendu** (bdesk-38k.74 ; liste blanche depuis le round 3, relecture finale). Quand du SQL stocké s'exécute dans une instruction, l'erreur de Dolt cite le contenu d'un fichier : `json_extract(load_file(f), '$')` rend « Invalid JSON text … "<contenu>" », `uuid_to_bin` « unable to parse '<contenu>' to UUID », `timestamp` « Incorrect datetime(6) value: '<contenu>' », `st_srid` et `from_unixtime` le contenu en octets (`[83 69 67 …]`) entre apostrophes (mesuré sur trente fonctions) ; `st_geomfromgeojson` en cite un caractère. Le contenu peut porter ses propres guillemets, apostrophes et sauts de ligne. **Et `from_base64` l'écrit sans aucune citation** : « illegal base64 data at input byte 4407630 », où le nombre (0x43414E, « CAN ») est un octet du fichier lu par l'expression qui a produit la chaîne invalide ; un index fonctionnel `((from_base64(concat(repeat('A', conv(hex(substr(load_file(f),1,3)),16,10)), '!'))))` en fait un oracle, un octet par lecture. Jusqu'au round 2, le client vérifié reprenait le texte d'une instruction de la lecture « jusqu'à la première citation qui n'est pas un nom écrit par la requête » (`withoutData`), et cette ADR écrivait qu'« aucune des trente fonctions essayées » n'écrivait sans citation : **c'était faux, et c'était une liste noire de ce qui peut se cacher dans un message** — la forme exacte qui a fait tomber les assertions précédentes. Le client vérifié ne rend donc plus ce texte, et ne le consigne pas non plus (le laisser dans le journal du serveur serait écrire, à côté de la base, ce qu'on refuse de lui montrer ; une option de journal reste possible, jamais sur la réponse HTTP) : (1) une **instruction de la vérification** (les premières du groupe : `DoltQueryError.completed` dit combien ont abouti avant celle qui échoue ; le diagnostic et la recherche du commit de base n'en ont que de telles) que Dolt refuse autrement que par son assertion n'a aucune raison de le faire, sinon du SQL stocké s'y est exécuté : message fixe (« La vérification du SQL stocké n'a pas pu s'achever : Dolt a refusé l'une de ses propres requêtes, dont le message n'est pas repris… »), rien de plus (la recherche d'une base voisine responsable, R5, est retirée) ; (2) une **instruction de la lecture** : un message fixe par classe de cause (`readFailure`) — `table not found: <nom>` et `column "<nom>" could not be found in any table in scope` disent ce qui manque (« Dolt ne trouve pas la table « issues » que l'app lit. »), mais **seulement quand `<nom>` est un nom que la requête envoyée écrit elle-même** (un mot d'au moins trois caractères de ses propres instructions : `issues`, `title`, jamais un contenu), et toute autre cause est « Dolt a refusé une lecture de l'app : le texte de son erreur n'est pas repris (il pourrait citer ce que la base lui fait lire). » Sans `completed` (la sortie de Dolt n'a pas pu se lire), on ne sait pas laquelle a échoué : le message fixe de la lecture. Les erreurs que le client écrit lui-même (délai dépassé, sortie trop volumineuse, binaire absent, trop de lectures en attente, « dolt a échoué (code de sortie N) sans message d'erreur ») ne sont pas du texte de Dolt et ne changent pas. **m4, round 4 : le texte de Dolt qui n'a pas la forme « error on line N for query » n'est pas rendu non plus.** `guarded` ne remplaçait que celui-là ; un verrou (« database "beads" is locked by another dolt process… »), une permission refusée, un plantage, ou `illegal base64 data at input byte N` quand rien n'a cité la requête, passaient tels quels dans la raison d'un Projet illisible. Le client marque maintenant ce qu'il a lu sur la sortie d'erreur de Dolt, et le fragment de sa sortie qu'il n'a pas su lire (`DoltTextError`, `errors.ts`, rendu par `toError` et `run`), et le client vérifié remplace chacun, **à chaque sortie** (`open` : `query`, `queryAll`, `storedSqlAt`, donc la recherche du commit de base, le diagnostic, la lecture, l'ancre d'une époque et les lectures qui ne nomment aucune table), par un message fixe de sa classe : le verrou (« La base est tenue par un autre processus dolt : réessayez dans un instant. », le drapeau `locked` demeure), la permission refusée (« Dolt ne peut pas ouvrir les fichiers de la base : permission refusée. »), la sortie illisible (« La sortie de dolt est illisible. », sans le fragment que l'analyse cite) et toute autre cause (« Dolt n'a pas pu lire la base : le texte de son erreur n'est pas repris… »). Les classes ne servent qu'à choisir entre des messages fixes : se tromper de classe ne cite rien. Le texte n'est ni rendu ni consigné (aucune `cause`).
- **Une base qui change pendant la vérification.** Quand l'assertion échoue et que le diagnostic, dans un autre processus, ne trouve rien, la lecture reprend : trois essais au plus, puis « La base change plus vite que la vérification… (3 essais) ». Deux causes y menaient, la lecture étant refusée dans les deux cas (relevées par les relectures de bdesk-38k.69 et .74) :
  1. **Une vue qui va et vient** (là quand la lecture part, partie quand le diagnostic passe) : le diagnostic ne peut pas la nommer. **Le dernier essai porte donc ses propres relevés** (`storedSqlEvidence`) : devant les deux assertions, les lignes des vues, des colonnes générées et des vues de HEAD qu'elles comptent, lues dans le même processus et la même transaction (les deux relevés d'`information_schema` devant la première assertion, celui des vues de HEAD, qui lit `dolt_schemas`, après elle, comme la seconde assertion). Quand une assertion échoue, Dolt s'arrête, mais sa sortie a déjà les documents des instructions d'avant, sans serveur comme derrière un serveur (vérifié avec Dolt 2.5.0) : le client les garde (`DoltQueryError.completed`, non énumérable : ce sont des lignes de la base), et le Projet est refusé en nommant ce que l'assertion a vu.
  2. **Un working set qui passe de sale à propre entre la lecture et le diagnostic, HEAD ne changeant pas** (la course de la relecture : un écrivain renomme une table, puis la rétablit, de sorte que le working set est sale puis propre, sans vue à nommer). Le diagnostic, propre, oubliait le HEAD, et la lecture suivante, sale de nouveau, échouait de nouveau, trois fois. Il retient maintenant le HEAD qu'il lit dans l'instantané propre (voir « HEAD et le working set »).

  Mesuré sur cette course (150 s, une base jetable servie par un `dolt sql-server` jetable, un écrivain qui fait aller et venir une vue hostile, trois lecteurs ; deux tours, la machine à une charge de 33 à 242), l'erreur générique terminait **14 lectures sur 480 sur 741b196** (2 sur 287 à charge modérée, 12 sur 193 à charge forte), **1 sur 448 avec les relevés seuls** (la première livraison de bdesk-38k.74) et **0 sur 389 avec le HEAD retenu sur propre en plus** (test exact de Fisher, unilatéral, contre 741b196 : p ≈ 0,0002 ; contre la première livraison, la différence n'est pas significative : 1 sur 448 contre 0 sur 389, p ≈ 0,5, et ce qui garde le HEAD retenu sur propre est le test déterministe d'une base sale à chaque lecture et propre à chaque diagnostic, non cette course). La première livraison avait annoncé 0 sur 211 d'après une seule exécution ; la relecture avait trouvé 18 sur 278, puis 2 sur 223 : le zéro ne se déduit pas d'une course, qui dépend de la charge. Aucune course n'a créé de fichier ni rendu de ligne de la base hostile. **Ce qui peut rester générique** (non observé en 389 lectures) : HEAD qui change entre deux essais d'un working set sale, ou un diagnostic qui n'a pu retenir aucun HEAD avant le dernier essai parce qu'une vue ou un commit arrive entre ses temps : « La base change plus vite… » est alors exact. Si une version de Dolt n'écrivait plus les documents des instructions réussies avant l'erreur, `completed` serait absent et le dernier essai dirait de même « La base change plus vite… » : la lecture est refusée dans tous les cas, jamais lue.
- **Hors du périmètre de l'app : ce qui s'exécute quand bd écrit.** Les valeurs par défaut calculées (`default (load_file(…))`) et les déclencheurs d'une base partagée s'exécutent à l'écriture, donc quand **bd** écrit sur la machine de celui qui tire la base, jamais quand l'app lit (mesuré : la valeur est fixée à l'insertion, la table et son historique ne la recalculent pas, et un déclencheur ne part que d'un `insert`). L'app n'écrit jamais : ce que bd exécute n'est pas ce que cette vérification garde.
