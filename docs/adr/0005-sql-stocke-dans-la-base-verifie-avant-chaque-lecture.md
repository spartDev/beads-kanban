# Le SQL que la base porte (vue, colonne générée) est vérifié avant chaque lecture, dans le même processus

Le garde de lecture seule (`src/server/dolt/read-only.ts`, bdesk-38k.56 et 38k.63) juge le texte de la requête, jamais ce que la base contient. Or Dolt exécute du SQL qui est dans la base : une **vue** (`select … from issues` lit la vue `issues` si la base en a une, avec n'importe quelle définition, `load_file('<base>/…')` ou `dolt_query_diff('select … into outfile …', …)` compris) et une **colonne générée** (`title varchar(500) generated always as (load_file(…)) virtual`, évaluée à chaque lecture, de la table comme de son historique). Le contenu d'une base beads vient d'un remote partagé : un collaborateur peut commiter l'une ou l'autre, et la lecture ordinaire de l'app rend alors le contenu d'un fichier de la machine, ou crée un fichier (relevé par la relecture finale de bdesk-38k.63, N1, antérieur à .63). La portée est bornée par `secure_file_priv`, que `dolt sql` pose sur le dossier de la base. Mesuré sur dolt 2.5.0 (`proofs/bdesk-38k.69.md`) :

- c'est la vue du **working set** que Dolt exécute, même pour `… as of 'HEAD'` (une vue qui n'est que dans le commit n'est pas résolue) ; une vue peut porter le nom d'une table système (`dolt_log`, `dolt_status`, `dolt_schemas` : `create view` l'admet, et la vue masque la table), y compris celle que la vérification elle-même lit ;
- ni un déclencheur (il ne part que d'une écriture), ni un événement (`dolt sql` ne lance pas le planificateur à la lecture), ni une procédure (elle ne part que d'un `call`, que le garde refuse) ne s'exécute à la lecture ;
- bd crée lui-même deux vues, `ready_issues` et `blocked_issues`, dans toutes ses bases (relevé sur cinq copies de bases réelles) : « aucune vue » refuserait tous les Projets.

## Considered Options

- **Refuser toute base qui a une vue** — rejeté : fausse alerte sur toutes les bases beads.
- **Une vérification dans un processus à part, mémorisée par HEAD** (la piste du ticket) — rejetée : un commit, ou une vue du working set, qui arrive entre la vérification et la lecture est exécuté ; et le HEAD seul ne dit rien du working set, que Dolt exécute.
- **Restreindre `secure_file_priv` pour les processus que l'app lance** — impossible : la variable est en lecture seule (`set` la refuse, `set persist` aussi), la configuration persistée (`sqlserver.global.secure_file_priv`, globale ou de la base) et l'environnement n'y font rien, et `dolt sql` la pose sur son dossier de données, que l'app ne peut pas rendre plus étroit que celui de la base (`--data-dir` ou `-C` l'élargissent au dossier parent ; un lien symbolique vers la base n'est pas suivi). Un bac à sable du système ne se porte pas d'un poste à l'autre.
- **Deux instructions qui précèdent chaque lecture, dans le même processus** — retenu. Dolt s'arrête à la première erreur d'un groupe : une sous-requête scalaire qui rend plusieurs lignes (« the subquery returned more than 1 row ») dès qu'il y a du SQL stocké empêche la lecture de partir. Aucun délai ne sépare la vérification de la lecture : la base est vérifiée dans l'état exact où elle est lue.

## Consequences

- **Quoi** (`src/server/dolt/stored-sql.ts`). Les noms que l'app lit (`reader.ts`, `history.ts`) : `issues`, `dependencies`, `labels`, `comments`, `config` et les tables système `dolt_history_issues`, `dolt_history_dependencies`, `dolt_log`, `dolt_commit_ancestors`. Une vue qui porte l'un de ces noms, ou celui d'une table que la vérification lit (`dolt_schemas`, `dolt_status`), est refusée ; une colonne générée d'une de ces tables aussi. `ready_issues` et `blocked_issues` ne sont jamais lues : elles sont admises. **Une lecture de plus d'une table, ou d'une autre, se déclare dans cette liste** : `stored-sql.test.ts` refait chaque lecture de l'app et échoue si elle nomme une table que la liste ne surveille pas.
- **Les noms ne se comparent que dans Dolt, jamais en JavaScript.** Dolt lit un nom à sa façon : `Issues` est `issues` ; une vue `issueſ` (U+017F, le « s long ») est lue comme `issues` (il replie la casse à l'unicode), alors que `'ſ'.toLowerCase()` reste `ſ` ; `İ` (U+0130) est ramené à `i` quand Dolt crée la vue. Une comparaison en JavaScript manque ce que Dolt réunit, et c'est un trou : la relecture de bdesk-38k.69 en a trouvé deux (une table `Issues` que `dolt_status` écrit autrement, une vue `dolt_history_dependencieſ`). Toute comparaison de nom se fait donc **dans Dolt** : par sa collation (`information_schema.views` et `.columns`, `dolt_schemas.name`, qui ignorent la casse et plus : un balayage de 1 124 caractères que la casse, la compatibilité ou les accents rapprochent d'une lettre des noms lus n'a trouvé, pour les vues, que `ſ` et `İ` que Dolt lise comme un nom lu, et aucun que ces comparaisons laissent passer ; pour les tables, que `İ`, de même), ou par sa résolution même (`show full columns from <nom lu> as of 'HEAD'`). Le seul nom comparé en JavaScript l'est à une liste fermée, par égalité exacte, avec le refus pour cas par défaut (les deux vues de bd). `stored-sql.test.ts` le pin : aucun `toLowerCase`, `toUpperCase` ni comparaison locale dans `stored-sql.ts`.
- **Dans quel ordre.** La première instruction ne lit que `information_schema.views`, que rien ne masque : une vue nommée `dolt_status` ou `dolt_schemas` arrêterait la seconde, qui lit ces tables, avant qu'elle ne les exécute. La seconde lit les vues de HEAD, les colonnes générées du working set (`information_schema` ne se lit pas `as of`) et `dolt_status`.
- **HEAD et le working set.** Les lectures `as of 'HEAD'` utilisent le schéma de HEAD ; `information_schema` donne celui du working set. Quand le working set est propre (bd en auto-commit, le défaut), ils sont le même et rien ne se retient. Quand il a changé sans commit (`batch`, `off`), **une table quelconque** (`dolt_status` a une ligne, sans qu'on en compare le nom : il écrit `Issues` quand la table a été renommée ainsi, que `dolt_status` y compare ou non à `issues`), l'assertion échoue tant qu'elle ne porte pas le HEAD dont le schéma a été vérifié. Un diagnostic, en trois temps, le vérifie et le retient par base : il lit `show full columns from <table> as of 'HEAD'` de **chacune des tables lues, par son nom** (Dolt le résout comme la lecture le fera), dans le même processus que `hashof('HEAD')`, et sonde une à une celles dont HEAD manque (« table not found »). Il échoue de nouveau à chaque commit tant que le working set est modifié.
- **Une base de révision** (les époques du schéma des dépendances, `<base>/<commit>.dolt_history_dependencies`, `history.ts`) est relue par `show columns` (la colonne générée) et `show full tables from <base>/<commit>` : lire sa table `dolt_schemas` exécuterait la vue qui la masque (mesuré). Un commit ne change pas : cette vérification vaut pour la lecture qui suit. **Toute vue y est refusée, sauf `ready_issues` et `blocked_issues`**, admises par égalité exacte avec leur nom : une base de révision ne lit rien d'autre, et on ne sait pas reconnaître par son nom la vue que Dolt lit comme `dolt_history_dependencies` (voir la règle des noms). Les deux vues de bd sont les seules qu'ait jamais portées l'un des 1 633 commits des cinq copies de bases réelles. L'époque se dit par son commit (« époque du commit 0gegu6r6 »), non par le nom de la base de révision, qui porte le hash entier.
- **Le coût** : 14 à 16 ms de CPU par processus de lecture (95 à 107 ms à vide, mesuré sur quatre copies de bases réelles), dont 9 pour `information_schema.columns` : chaque balayage est compté dans une table dérivée du `from`, ce qui coûte moitié moins que dans la sous-requête scalaire ; une lecture qui ne nomme aucune table (`select hashof('HEAD')`, le sondage du direct, ADR 0002) n'en porte pas. Un diagnostic (deux à trois processus) n'a lieu qu'à la première lecture d'une base dont le working set est modifié sans commit, puis à chaque commit tant qu'il l'est.
- **Où il s'installe** : `createCheckedDoltClient`, le client par défaut de `createProjectService` et de `discoverProjects`. Un client passé à la main (les essais, avec un faux `dolt`) n'a pas la vérification : seuls les essais le font.
- **Le refus** est un `StoredSqlError`, une `DoltQueryError` : un Projet illisible (503 « Projet illisible : … SQL stocké dans la base… »), dont la raison nomme l'objet (sans citer son contenu).
